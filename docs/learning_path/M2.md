## 一、M2 要做什么（一句话）

**让系统能管理"基础数据"**：训练阶段（Phase）和动作库（Exercise）的增删改查。

M1 系统能登录了，但登录进去没东西可看。M2 把地基数据建起来：
- **阶段**：一段连续的训练时期（如"备赛期"），创建 → 查看 → 归档（只读）→ 启用
- **动作库**：用户自己的动作清单（如"深蹲"），带部位分组、默认组次、要领

M2 之后，M3 才能建计划、M4 才能记训练——**没有地基，上层全白搭**。

## 二、核心概念（先理解再动手）

### 2.1 为什么需要"用户自己的数据"（user_id 隔离）

所有表都有 `user_id` 字段。为什么？

> 这是**多用户系统**：admin 的动作库 ≠ user1 的动作库。
> 每个用户只看到、只操作自己的数据——这就是"数据隔离"。

实现上：所有 SQL 都带 `WHERE user_id = ?`，`?` 绑定当前登录用户。
**绝不能查所有用户的数据**（安全漏洞）。

### 2.2 阶段的生命周期

```
创建（进行中）→ 训练（M3/M4 用）→ 归档（archived=1，只读）→ 可重新启用
```

- 进行中阶段：可建计划、可记记录（M3/M4 的事）
- 已归档阶段：只读，不可新增（防止改历史数据）

M2 只做 CRUD + 归档/启用切换，不涉及训练本身。

### 2.3 动作库：每个动作的"默认值"设计

动作库是"字典"：存的是**动作的默认信息**，不是某次训练。

```
Exercise { name, body_part, default_mode, bar_weight, default_sets, default_reps, key_points }
```

- `default_sets/reps`：建计划时预填（M3 用）
- `bar_weight`：杠铃片空杆重（M4 算重量用）
- `body_part`：部位分组（胸/背/腿/肩/臂/核心），筛选用

> **默认值语义：由前端实现，不在后端判断**。表单页预填这些默认值
> （下拉框默认选中 / 输入框 value 预填），用户可见可改；
> 后端只 parse 收到的值，不判断"空串 → 默认"。
> 数据库列 DEFAULT 仅是兜底（正常流程不会触发）。

M2 先把这些数据管起来，M3/M4 才知道"该预填什么"。

## 三、M2 的 6 个步骤

> 顺序：**先打地基（AuthUser 守卫），再建数据（阶段 → 动作）**。
> 为什么不先写 handler？M1 的守卫方案（函数体内 require_user）会导致每个
> handler 都重复守卫代码。M2 有 14 个 handler，先做 AuthUser 提取器，
> 后面所有 handler 签名里直接要 AuthUser，一次搞定、零返工。

### 第 1 步：登录守卫改造（方案 A：AuthUser 提取器）★ 本阶段难点

M1 用的是方案 B（每个 handler 函数体内调用 `require_user`）。
M2 页面大量出现，M1 写法会导致**每个函数都重复写守卫代码**：

```rust
// M1 写法（每个 handler 都要重复）：
async fn list(State(state): State<AppState>, headers: HeaderMap) -> Result<..., AppError>
{
    let user = require_user(&state, &headers).await?;   // ← 每个函数都写
    ...
}
```

**M2 改造为方案 A：自定义提取器 `AuthUser`**，把"验证登录 + 取用户"封装成提取器：

```rust
// M2 写法（守卫在签名里，axum 自动注入）：
async fn list(State(state): State<AppState>, user: AuthUser) -> Result<..., AppError>
{
    // user 已经是登录用户，不需要手动 require_user
}
```

实现要点（老师注释会写）：
- `impl FromRequestParts<AppState> for AuthUser`（M1 学过这个 trait 是"提取器许可证"）
- 内部读 `parts.headers` 的 cookie → `auth::get_user_by_session` → `User`
- 失败返回 `AppError::Unauthorized`（401）

**为什么现在做？** M2 页面 14 个 handler 全部要登录，M1 写法会重复 14 次守卫。
方案 A 是 axum 正统做法，M1 时没引入是怕概念太多，现在水到渠成。

**放哪？** `src/handlers/auth.rs` 末尾（它是认证逻辑的归属地）。

### 第 2 步：`src/handlers/phases.rs` —— 阶段 handler（CRUD + 归档）

新建文件 `src/handlers/phases.rs`，老师会写定义 + 教学注释，学生实现。

需要的函数（7 个）：

| 函数 | 方法/路由 | 作用 |
|------|----------|------|
| `list` | GET `/phases` | 阶段列表（进行中/已归档分区） |
| `create_form` | GET `/phases/new` | 创建阶段表单页 |
| `create` | POST `/phases` | 创建阶段 |
| `edit_form` | GET `/phases/{id}/edit` | 编辑表单页 |
| `update` | POST `/phases/{id}/edit` | 更新阶段 |
| `archive` | POST `/phases/{id}/archive` | 归档（archived=1） |
| `unarchive` | POST `/phases/{id}/unarchive` | 重新启用（archived=0） |

关键知识点（老师注释里会写）：
- `Path<i64>` 提取器：从 URL 拿 id
- 归档/启用的"切换"本质是 `UPDATE ... SET archived = ?`
- 数据隔离：所有查询带 `user_id`
- 守卫：签名里 `user: AuthUser`（第 1 步的成果）

## 六、M2 常见坑

| 坑 | 解决办法 |
|---|---|
| `Path<i64>` 提取失败 404 | 路由路径用 `{id}` 占位符（axum 0.8 语法），不是 `:id` |
| 表单 POST 400 | `Form<T>` 字段名要和 HTML `name` 一致 |
| 归档后还能编辑 | 归档阶段应禁止 edit/update，返回 403 或提示 |
| 数据隔离漏洞 | 所有 SQL 必须带 `WHERE user_id = ?`，不能只按 id 查 |
| 守卫重复代码 | 用 `AuthUser` 提取器（第 4 步），不要在 handler 里手写 |
| 大括号换行 | 项目约定：函数体左大括号换行（Allman 风格） |
| 禁止 unsafe（项目规则） | 任何地方都别用 unsafe |

### 参考答案（先自己写，再对照）

<details>
<summary>点击展开参考答案</summary>

**第 1 题**：所有 SQL 都带 `WHERE user_id = ?`，`?` 绑定当前登录用户的 id。
查询、更新、删除都只作用于 `user_id = 当前用户` 的行。
（绝不能只按 id 查，否则能查到别人的数据。）

**第 2 题**：`UPDATE phases SET archived = 1 WHERE id = ? AND user_id = ?`。
归档 = 改一个字段（archived 0→1），数据还在，只是变成只读。
重新启用 = 再改成 0。不是删除！

**第 3 题**：默认值/元数据。`default_sets` 是"建计划时预填的组数"，
`bar_weight` 是"空杆重量"（算总重用）。动作库是字典，不是某次训练记录。

**第 4 题**：方案 A 把守卫放进 handler 的**签名**（参数位置），axum 自动注入。
方案 B 每个函数都要**手动调用 require_user**（重复代码）。
方案 A 是"声明式"（签名里说"我要登录用户"），方案 B 是"命令式"（自己调函数）。

**第 5 题**：`{id}` 占位符匹配到的 URL 片段。路由 `/phases/3/edit` 的 `3` 就是 id。
axum 自动把 URL 里的 `{id}` 部分解析成 `i64` 传给 `Path(id)`。
