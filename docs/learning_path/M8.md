## 一、M8 要做什么（一句话）

**给 train_record 加一层 `/api/v1/...` 的 JSON 接口**——把"人看的页面"和
"程序读的数据"分开，为 M9 的 iced 桌面客户端铺路。

M7 之后 web 版已经完整可用，但它是**服务端渲染（SSR）**：HTML 在服务器拼好
发给浏览器。桌面客户端（iced）要的是**结构化数据（JSON）**，不是 HTML。
M8 就是补上这一层：**同一个数据库、同一套业务逻辑，多一个"程序入口"**。

### 为什么是 REST API 而不是别的？

| 方案 | 结论 | 理由 |
|------|------|------|
| **REST API（JSON over HTTP）** | ✅ | iced 客户端跨进程访问服务器，HTTP 是唯一通用通道；JSON 是事实标准 |
| 直接在 iced 里连 SQLite | ❌ | 数据库在服务器上，GUI 在电脑上，无法直连远程 SQLite |
| GraphQL / gRPC | ❌ | 学习成本高、工具链重；个人项目 REST 完全够用 |

## 二、核心概念（先理解再动手）

### 2.1 前后端分离：什么是"API 层"

```
现在（M0-M7，SSR 服务端渲染）：
  浏览器 → GET /today → 服务器查库 + 拼 HTML → 返回完整页面（人看）

M8 之后（API 层）：
  iced 客户端 → GET /api/v1/today → 服务器查库 + 拼 JSON → 返回结构化数据（程序读）
```

同一套数据、同一个数据库，**两种出口**：
- 页面路由（`/today`、`/exercises`...）→ HTML，给人看
- API 路由（`/api/v1/...`）→ JSON，给程序读

**为什么不改造现有 handler 返回 JSON？**
页面 handler 职责是"渲染 HTML"，返回 JSON 会破坏它。
M8 的做法是**新增一组 API handler**，与页面 handler 并列。

### 2.2 JSON 序列化：serde 的 Serialize

页面返回 `Html<String>`（拼好的字符串），API 返回 `Json<T>`（结构化数据）。
Rust 里把结构体变成 JSON 靠 **serde 的 `Serialize`**：

```rust
#[derive(Serialize)]
struct PhaseOut
{
    id: i64,
    name: String,
    archived: bool,
}

// 返回：Json(phase_out)  →  {"id":1,"name":"phase1","archived":false}
```

关键：**模型（models.rs）和 API 输出（DTO）要分开**。
原因：
1. 模型字段是数据库列的镜像（`password_hash` 等），不能直接暴露
2. API 输出可能比模型多/少字段（如动作详情要带 `1rm`，模型没有）
3. 安全：绝不把 `password_hash` 序列化出去

DTO（Data Transfer Object，数据传输对象）= 专门给 API 用的输出结构体。

### 2.3 ApiError：API 的错误要 JSON，不能 302

M7 第 2 步把页面错误改成了 302 跳登录页（给人看）。
但 API 客户端（iced）**不需要跳转**，它要的是**状态码 + JSON 错误信息**：

```json
{"error": "未登录"}
```

所以 API 层需要自己的错误类型 `ApiError`：

```rust
impl IntoResponse for ApiError
{
    fn into_response(self) -> Response
    {
        let (status, message) = match self { ... };
        (status, Json(json!({ "error": message }))).into_response()
    }
}
```

**为什么不能复用 AppError？**
`AppError` 的 `Unauthorized` 已经实现了 302 跳转——API 客户端收到 302
会跟随跳转去 `/login` 拿 HTML，而不是拿到 JSON。语义不同必须分开。

### 2.4 API 认证：复用 session cookie

iced 客户端也是 HTTP 客户端，同样可以带 Cookie。
所以 API 认证**复用现有 session 机制**：

```
POST /api/v1/login  {username, password}
  → 服务器验证 → 创建 session → Set-Cookie: session=xxx
  → 返回 {"user": {...}, "token": "xxx"}（token 是给非浏览器客户端用的）

GET /api/v1/today  带 Cookie: session=xxx
  → AuthUser 提取器验证 → 返回 JSON
```

两种客户端：
- **浏览器**（调试 API）：cookie 自动带上
- **iced**：手动保存 token，每次请求带 `Authorization: Bearer xxx` 或 Cookie 头

M8 教学上先用 **Cookie 认证**（复用 AuthUser 提取器，改动最小）。
token 认证（Authorization 头）作为扩展点写在 todo.md。

### 2.5 复用业务逻辑 vs 复制 SQL

API handler 和页面 handler 会查**同一批数据**（today、phases、exercises...）。
两种做法：

| 做法 | 说明 | 结论 |
|------|------|------|
| 复制 SQL | API handler 里再写一遍 `SELECT * FROM phases...` | ❌ 双份 SQL 易漂移（改一处忘另一处） |
| **抽公共查询函数** | 把"查某阶段列表"等逻辑抽到 `handlers/` 外的 `services/` 或独立函数 | ✅ 单一事实来源 |

M8 的做法：**先复制，后抽取**。
第一版 API handler 可以直接写 SQL（快速跑通），
当发现同一查询在 2 个以上 handler 出现时，抽成公共函数。

### 第 1 步：ApiError —— `src/api/mod.rs`

新建 `src/api/mod.rs`，定义 API 错误类型：

```rust
// src/api/mod.rs
#[derive(Debug)]
pub enum ApiError
{
    Database(sqlx::Error),
    Unauthorized,
    NotFound(String),
    Validation(String),
    Forbidden(String),
    Other(String),
}

impl IntoResponse for ApiError
{
    fn into_response(self) -> Response
    {
        let (status, message) = match self
        {
            ApiError::Database(e) =>
            {
                tracing::error!("API 数据库错误: {e}");
                (StatusCode::INTERNAL_SERVER_ERROR, "数据库错误".to_string())
            },
            ApiError::Unauthorized =>
            {
                (StatusCode::UNAUTHORIZED, "未登录".to_string())
            },
            ApiError::NotFound(msg) => (StatusCode::NOT_FOUND, msg),
            ApiError::Validation(msg) => (StatusCode::BAD_REQUEST, msg),
            ApiError::Forbidden(msg) => (StatusCode::FORBIDDEN, msg),
            ApiError::Other(msg) => (StatusCode::INTERNAL_SERVER_ERROR, msg),
        };
        // 关键：返回 JSON 而不是 302！
        (status, Json(json!({ "error": message }))).into_response()
    }
}
```

**改造 AuthUser**：`AuthUser` 的 `Rejection` 目前是 `AppError`。
API handler 用 `AuthUser` 时，未登录会返回 302——不行！
方案：API 用自己的守卫，或者把 `AuthUser` 泛型化。

> 教学简化：M8 先定义 `ApiAuthUser`（复制 AuthUser 的提取逻辑，
> Rejection 换成 ApiError）。M9 iced 客户端开始前，再考虑统一。

**路由接线**（main.rs）：
```rust
// 在 Router::new() 里追加（与页面路由并列）

```

### 第 2 步：登录/登出 API —— `src/api/auth.rs`

端点：

| 方法 | 路径 | 说明 |
|------|------|------|
| POST | `/api/v1/login` | 登录，返回 `{"user": {...}}` + Set-Cookie |
| POST | `/api/v1/logout` | 登出 |
| GET | `/api/v1/me` | 当前登录用户（API 认证自检） |

实现要点：
- `login`：复用 `auth::verify_password` + `auth::create_session`（已有函数）
- 返回 `Json(UserOut)`（`password_hash` 不序列化！）
- 用 `ApiAuthUser` 守卫 `me`

```rust
// src/api/auth.rs
#[derive(Deserialize)]
pub struct LoginReq
{
    pub username: String,
    pub password: String,
}

#[derive(Serialize)]
pub struct UserOut
{
    pub id: i64,
    pub username: String,
    pub is_admin: bool,
    pub body_weight: Option<f64>,
}

impl From<&User> for UserOut
{
    fn from(u: &User) -> Self
    {
        Self { id: u.id, username: u.username.clone(), is_admin: u.is_admin, body_weight: u.body_weight }
    }
}
```

### 第 1 题

页面层的消费者是**人（浏览器）**，302 会带人去登录页，体验好。
API 层的消费者是**程序（iced 客户端）**，它不想要"跳转指令"——
它要明确的"你没登录"信号（401）来决定弹登录框。如果 API 返回 302，
iced 会默默跟随跳转去拿 /login 的 HTML，然后解析失败（拿到的是 HTML 不是 JSON）。

### 第 2 题

`User` 里有 `password_hash`（argon2 密码哈希）。如果直接序列化整个结构体，
密码哈希就泄露到 API 响应里了（虽然不可逆，但绝不该暴露）。
所以 API 输出用 DTO（`UserOut`），只挑安全的字段（id/username/is_admin/body_weight），
用 `From<&User>` 转换。

### 第 3 题

M8 用 **Cookie 认证**（session cookie，与页面同一套）。
浏览器自动带 cookie；iced 客户端需要手动保存服务器返回的 token，
在后续请求的请求头里手动带 `Cookie: session=xxx`。
（M8 教学简化版；未来可扩展 `Authorization: Bearer xxx` 头认证，见 todo.md。）

### 第 4 题

页面表单用 `serde_urlencoded` 解析，它是 **map 语义**（后值覆盖前值）。
API 用 `serde_json` 解析，JSON 数组（`[...]`）天然是**有序列表**——
`items` 字段是 `Vec<Item>`，每个元素独立，顺序就是数组顺序，
不存在"键覆盖"问题。这正是 API 比表单更适合程序传复杂数据的原因。

### 第 5 题

不是。1RM 是**算出来的**（纯函数 `calc::epley_1rm(weight, reps)` 实时计算），
不落库。records 表只存原始数据（重量/次数），1RM 是展示层指标——
存了反而有"数据漂移"风险（改了记录忘记更新 1RM）。
calc.rs 的定位就是"纯函数、无状态、可单测"，M8 复用它即可。
