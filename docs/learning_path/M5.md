## 一、M5 要做什么（一句话）

**让训练历史"可回溯"**：日历看哪天练过 → 点日期看当天全部记录 → 进动作详情页
看该动作的历史表格 + 重量/1RM 折线图。

M4 把"训练时"记下来了（records 落库），M5 把"训练后"的回顾做出来——
**渐进超负荷分析的数据入口**。M5 是只读为主的阶段：查数据、算指标、画图表，
几乎不写数据（除了打磨项）。

## 二、核心概念（先理解再动手）

### 2.1 三张页面，层层下钻

```
/history（历史首页）           → 日历 + 按阶段列出的训练日列表
  └─ 点某天 /history/{date}    → 当天全部动作记录
       └─ 点某动作 → 动作详情 /exercises/{id}/stats
                         → 该动作全部历史表格 + 重量/1RM 折线图
```

- 日历视图：当月月历，**有记录的日子做标记**，点日期 → 当天记录列表
- 日期列表：按阶段（phase）列出所有训练日（`DISTINCT record_date`）
- 动作详情：某动作全部历史 + 折线图，是"渐进超负荷"的观察窗口

### 2.2 1RM 是什么，为什么算

**1RM（One Rep Max）**：某个动作你理论上最多能举起一次的重量。
但你不会每天测 1RM（危险），所以用**估算公式**从日常记录反推：

- **Epley 公式**（从"实际重量 × 次数"估 1RM）：
  `1RM = W × (1 + reps/30)`
- **Wathan 公式**（从 1RM 反推"目标次数下的预估重量"MRM）：
  `MRM = 1RM / (1.67 − 0.067 × target_reps)`
  展示 1RM / 2RM / 3RM（target_reps 分别取 1 / 2 / 3，与旧 sys.py 一致）

**为什么要公式而不是直接存 1RM？**
因为一条记录是"60kg × 8 次"，直接比重量不公平（8 次比 4 次累）。
Epley 把不同次数归一化成"同一个可比数字"，才能画趋势线看进步。

### 2.3 纯函数与 UI 分离（calc.rs 的定位）

1RM 计算是**纯函数**（输入数字 → 输出数字，无副作用、无 IO）。
放在独立模块 `src/calc.rs`，好处：

- 可以单独写单元测试（`#[cfg(test)]` 直接 assert）
- 页面渲染只负责"取数据 + 调用 calc + 展示"，业务逻辑不散落各处

```rust
// 纯函数示例
pub fn epley_1rm(weight: f64, reps: i64) -> f64
{
    weight * (1.0 + reps as f64 / 30.0)
}
```

### 2.4 图表怎么画（Chart.js + 数据注入）

图表用 **Chart.js**（CDN 引入，structure.md §3 已定）。服务端只做两件事：

1. 把历史记录查出来，算好每条的 1RM
2. 序列化成 JSON，**注入到页面 JS 变量**（M4 修订已用过这招：`PART_ORDER`）

```
serde_json::to_string(&points) → var CHART_DATA = [...] → Chart.js 画折线
```

前端不重新请求接口、不手写数据——和 M4 的 `PART_ORDER` 注入同一模式
（补课文档 §10.3：配置单一来源的变体——数据单一来源）。

## 三、M5 要做什么（分步）

### 第 1 步：`src/calc.rs` —— 1RM 纯函数模块（新建）

文件：`src/calc.rs` + `src/main.rs` 加 `mod calc;`（或用 `mod.rs` 统一声明）

| 函数 | 签名 | 作用 |
|------|------|------|
| `epley_1rm` | `(weight: f64, reps: i64) -> f64` | Epley：`W × (1 + reps/30)` |
| `wathan_mrm` | `(one_rm: f64, target_reps: i64) -> f64` | Wathan：`1RM / (1.67 − 0.067 × target_reps)` |

要求：
1. 纯函数，**不碰数据库、不碰 IO**
2. 边界：`weight <= 0` 或 `reps <= 0` 时返回 0（无效记录不算 1RM）
3. 附带单元测试（`#[cfg(test)]`）：手算几个值断言
   - `epley_1rm(60.0, 8)` ≈ 76.0（60 × (1 + 8/30)）
   - `wathan_mrm(100.0, 2)` ≈ 65.1（100 / (1.67 − 0.134)）
   - 无效输入返回 0

### 第 2 步：`src/handlers/stats.rs` —— 历史首页（新建）

文件：`src/handlers/stats.rs` + `src/handlers/mod.rs` 加 `pub mod stats;`

| 路由 | 方法 | 功能 |
|------|------|------|
| `/history` | GET | 日历 + 日期列表 |

逻辑：
1. 守卫 `AuthUser`，查当前用户全部**非空训练日**：
   ```sql
   SELECT DISTINCT record_date FROM records
   WHERE user_id = ? ORDER BY record_date DESC
   ```
2. 按阶段分组展示训练日（可选增强）：JOIN phases 拿阶段名；
   简化版可直接平铺日期列表
3. 日历：取"今天所在月"（`strftime('%Y-%m', date('now','localtime'))`），
   查当月有记录的日期集合（`WHERE record_date LIKE '2026-08%'` 或
   `BETWEEN 月初 AND 月末`——用 SQLite 字符串日期运算，**不引入 chrono**），
   渲染 7 列月历网格（表格），有记录的格子加标记 + 链接到 `/history/{date}`
4. 无任何记录 → 空态提示"还没有训练记录，去今日页开始第一次训练吧"

### 第 3 步：当天详情页（GET /history/{date}）

| 路由 | 方法 | 功能 |
|------|------|------|
| `/history/{date}` | GET | 某天全部记录（只读） |

逻辑：
1. 守卫 `AuthUser` + `Path(date): Path<String>`（日期字符串，校验格式 `YYYY-MM-DD`）
2. 查该天记录：
   ```sql
   SELECT * FROM records WHERE user_id = ? AND record_date = ? ORDER BY created_at
   ```
3. 动作名：**沿用 M4 模式**——查全部动作 → `HashMap<i64, String>`（id → 名字）索引。
   为什么不用 JOIN？`query_as` 按列名匹配结构体字段，JOIN 多出的 `exercise_name`
   列与 `Record` 不匹配（M4.md 第 1 步已讲过）。想用 JOIN 就得定义新结构体——
   M5 教学上先沿用 HashMap 模式（注释里提一句 JOIN + View 结构体是备选）
4. 每条记录显示：动作名、重量、组×次、休息、感受、策略、要领、
   换算 1RM（Epley，调用 calc.rs）——1RM 放这页是顺手增强，重点在第 4 步
5. 顶部：返回历史首页链接；该天无记录 → 空态

### 第 4 步：动作详情页（GET /exercises/{id}/stats）★ 本阶段重点

| 路由 | 方法 | 功能 |
|------|------|------|
| `/exercises/{id}/stats` | GET | 动作历史表格 + 折线图 + 1RM |

> 注意：`/exercises/{id}` 本身没被占用（`/exercises/{id}/edit` 是编辑页），
> 但用 `/stats` 后缀语义更明确，也避免和未来路由冲突。

逻辑：
1. 守卫 `AuthUser` + `Path(id)`，先查动作存在且属于当前用户
   （`WHERE id = ? AND user_id = ?`——数据隔离纪律，M2 就学过的）
2. 查该动作全部记录：
   ```sql
   SELECT * FROM records WHERE user_id = ? AND exercise_id = ? ORDER BY record_date, id
   ```
3. 表格：日期 | 重量 | 组×次 | 1RM(Epley) | 感受 | 策略（策略是渐进超负荷的关键输入）
4. 折线图数据：每组 `(record_date, weight)` 和 `(record_date, epley_1rm)`
   两条线——**重量线看每次实际表现，1RM 线看进步趋势**
5. Chart.js CDN 引入（`<script src="https://cdn.jsdelivr.net/npm/chart.js"></script>`），
   数据用 `serde_json::to_string` 注入 `var CHART_POINTS = [...]`
6. 记录数 < 2 → 提示"记录太少，攒几次训练再看趋势"（避免空图）
7. 无记录 → 空态"这个动作还没有记录"

### 第 5 步：home 加入口

`src/main.rs` 的 home 里"训练管理"区加：
`<li><a href="/history">历史回顾（日历）</a></li>`

### 第 6 步：打磨项（todo.md §1.2）——模板/计划"空动作"校验

M3 遗留：创建模板/计划时一个动作都不勾选 → 生成空壳模板/计划。

## 六、M5 常见坑

| 坑 | 解决办法 |
|---|---|
| 引入 chrono 算日期 | 日历/日期全部用 SQLite 字符串运算（`strftime`/`date`），与 M3/M4 一致，不新增依赖 |
| `LIKE '2026-08%'` 当月过滤 | 可行（日期是零填充字符串），或 `record_date BETWEEN '2026-08-01' AND '2026-08-31'`；教学用 LIKE 更直观 |
| 折线图 X 轴是字符串日期 | Chart.js 默认按索引排，日期当 label 即可；排序靠 `ORDER BY record_date` 保证 |
| 1RM 除以零/负数 | `wathan_mrm` 分母 `1.67 − 0.067×target_reps` 在 target_reps ≥ 2 时为正；仍要在 calc 里防御 `<= 0` 返回 0 |
| 动作详情页查不到动作 | 先验证动作存在 + 归属，再查记录，否则 404 语义混乱 |
| 记录数太少画空图 | `< 2` 条显示提示文案，不渲染 Chart.js |
| 手写两处日期列表查询 | 日历（当月）与列表（全部）是两次查询，各取所需，别硬合成一个 |
| 大括号换行 | 项目约定：函数体左大括号换行（Allman 风格） |
| 禁止 unsafe（项目规则） | 任何地方都别用 unsafe |

**第 1 题**：查的是 **records 表**（当前用户的），
用 **`SELECT DISTINCT record_date`** 拿到"不重复的日期集合"。
当月日历再过滤 `LIKE '2026-08%'` 只看本月。

**第 2 题**：**8 次比 4 次累**。同样 60kg，做 8 次的人比做 4 次的人更强，
直接比重量会误判。Epley 把不同次数**归一化**成 1RM（同一个可比数字），
才能画趋势线看进步（渐进超负荷）。

**第 3 题**：**越高**。reps 越大括号里 **(1 + reps/30) 越大**，
1RM 越高——"同样的重量能做更多次 = 更强"，这就是渐进超负荷的量化。

**第 4 题**：折线图的横轴是**时间（日期）**，必须按**日期先后**排列，
否则图表前后乱跳、趋势无法阅读。

**第 5 题**：`query_as` 按**列名**匹配结构体字段，
JOIN 多出的 `exercise_name` 列与 `Record` 结构体**不匹配**，
无法直接映射。想用 JOIN 就得**定义一个新的 View 结构体**
（如 `RecordWithName`）——能写但要多一个结构体，数据量小时不值。
