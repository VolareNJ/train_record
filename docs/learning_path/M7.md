## 二、核心概念（先理解再动手）

### 2.1 热替换连接池：为什么需要 Arc + RwLock 两个一起上？

M6 上传 .db 后要重启，因为：
- 数据库文件被**连接池**占用，直接覆盖会损坏
- `AppState.pool` 是 handler 拿到的**不可变共享引用**，没法换掉

热替换的思路：把 pool 从"普通字段"升级成"锁里的字段"。

```
普通字段：AppState.pool: SqlitePool          → 只能读，不能换
升级后：  AppState.pool: Arc<RwLock<SqlitePool>> → 能读能写
```

两个包装各管一件事（缺一不可）：

| 包装 | 管什么 | 为什么需要 |
|------|--------|-----------|
| `Arc`（原子引用计数） | **共享所有权** | AppState 被 main 创建后 clone 给每个 handler，多个地方要**同时持有同一份** pool；Arc 让"一份数据多人共享"安全 |
| `RwLock`（读写锁） | **可变性** | 查询要**读**（并发随便读），换池要**写**（写时别人不能读）；RwLock = 多读者 + 单写者 |

#### 补充：RwLock（读写锁）和传统 Mutex（互斥锁）有什么区别？

一句话：**Mutex 连"读"也互斥，RwLock 只让"写"互斥。**

| | `Mutex<T>` | `RwLock<T>` |
|---|---|---|
| 同时几个线程能进 | **1 个**（读读也互斥） | **读：不限个；写：1 个** |
| 读读并发 | ❌ 排队 | ✅ 随便并发 |
| 读写并发 | ❌（没区别） | ❌（写时读要等） |
| 写写并发 | ❌ | ❌ |
| 实现成本 | 简单（一个标志位） | 复杂（读者计数 + 写者等待） |
| 适用场景 | 读少写多 / 临界区极短 | **读多写少** |

比喻：Mutex 是**单人自习室**——进去一个人就把门锁上，别人无论想看书还是写字都得等；
RwLock 是**阅览室**——大家随便进来读书（读锁），但管理员要**换一批书**时（写锁），
清场关门，换完再开门。

本项目为什么选 RwLock 而不是 Mutex？
- 查询（读锁）每秒发生无数次，handler 并发跑
- 换池（写锁）几乎从不发生（上传 .db 才一次）
- 读多写少 → RwLock 让"读"不互相排队，收益最大
- 反过来如果读少写多，RwLock 的维护成本反而拖慢，不如 Mutex

⚠️ 一个反直觉点：RwLock 的"写"要等**所有**在读的人出来，所以写锁**可能饥饿**
（读的人源源不断，写的人永远等不到）。本项目换池一年也遇不上几次，无所谓。

⚠️ 关键：SqlitePool 内部本身是 Arc 包装，`clone()` 只是引用计数 +1，**很便宜**。
所以 handler 每次查询前：

```rust
// 读锁 + 克隆快照（廉价，内部是引用计数）
let pool = state.pool.read().await.clone();
// 后续所有查询照旧用 &pool
```

换池时（backup_upload）：

```rust
// 写锁：换池期间所有查询阻塞等待
let mut pool = state.pool.write().await;
pool.close().await;                                        // 1. 等所有连接归还后关闭
fs::copy(&tmp_path, &state.config.database_path).await?;   // 2. 覆盖文件
*pool = SqlitePool::connect(&state.config.database_path).await?;  // 3. 换新池
```

⚠️ 会不会死锁？不会：写锁在握 → 其他 handler 抢不到读锁 → 拿不到连接 →
旧连接必然全部归还 → `close()` 完成。单用户工具并发低，安全。

### 2.2 401 vs 302：给"程序"看还是给"人"看？

| | 401 Unauthorized | 302 Found（重定向） |
|---|---|---|
| 本质 | 一个**状态码** | 一个**跳转指令** |
| 给谁看 | 程序/API 客户端（JSON） | 浏览器（人） |
| 体验 | 白屏 JSON 文本 | 自动跳转到登录页 |

现状：`AuthUser` 守卫失败 → `AppError::Unauthorized` → error.rs 输出 **401 JSON**
（浏览器直接显示 `{"error":"请先登录"}`，人看不懂）。

打磨：页面全部改成 **302 跳转 `/login`**。
⚠️ M8 的 REST API 需要 401 JSON（程序要判断"没登录"），
到时候 API 会用**自己的 ApiError 类型**，不受这里影响——M7 先全局跳转即可。

### 2.3 sort_order 的两笔旧账

**账 1（todo §1.1）：模板间排序是假的。**
`templates.sort_order` 创建时恒为 0，列表查询没有 `ORDER BY`。
修法：创建时取 `MAX(sort_order) + 1`（新模板排最后），列表 `ORDER BY sort_order, id`。

**账 2（todo §1.3）：编辑后动作顺序 ≠ 勾选顺序。**
编辑页用 `HashMap<String, String>`（serde flatten）收集勾选，**HashMap 迭代顺序不保证
等于表单提交顺序** → 先删后插时 sort_order 错乱。
修法：每行加一个隐藏序号 `order_{ex_id}`（渲染时 = 展示顺序），
JS `addRow` 给新行赋"当前最大序号 + 1"；后端按 order 值排序后再 enumerate 分配 sort_order。

### 2.4 PWA 两种缓存策略

| 策略 | 逻辑 | 用在哪 |
|------|------|--------|
| **Cache-first** | 命中缓存直接返回，没命中才走网络 | 静态资源（CSS/JS/图标），快 |
| **Network-first** | 先走网络（永远最新），失败才回缓存 | 页面/数据（/today、/plans/*），**断网兜底** |

M6 的 sw.js 全是 cache-first → 断网刷新 today 只显示静态壳，数据空白。
M7 升级：静态资源 cache-first + 页面请求 network-first，**断网也能看到上次的训练数据**。

### 2.5 systemd 部署

`nohup ... &` 的问题：重启服务器服务不回来、没有开机自启、进程管理靠手记 PID。
systemd 是 Ubuntu 的"进程管家"：写一个 `.service` 文件描述进程，
`systemctl enable` 开机自启、`Restart=on-failure` 崩溃自动拉起、
`journalctl -u` 看日志。

## 三、M7 要做什么（分步）

### 第 1 步：热替换连接池（核心打磨项）—— `src/main.rs` + 全部 handler

1. `main.rs` 的 `AppState`：
   ```rust
   pub struct AppState
   {
       pub pool: Arc<RwLock<SqlitePool>>,   // 原来是 SqlitePool
       pub config: AppConfig,
   }
   ```
   初始化时：`SqlitePool::connect(...)` 后包一层 `Arc::new(RwLock::new(pool))`。
   导入 `use tokio::sync::RwLock;`（tokio 已开 full feature）。
2. **所有 handler** 开头加一行快照，`&state.pool` 全部换成 `&pool`：
   ```rust
   let pool = state.pool.read().await.clone();
   ```
   机械替换：`grep -rn "state.pool" src/` 逐个看，`&state.pool` → `&pool`。
   ⚠️ 注意事务写法：`state.pool.begin()` → `pool.begin()`。
3. `backup_upload` 改为热替换（见 §2.1 代码），页面提示从
   "请重启服务生效" 改为 "已生效"。
4. 验证：上传 .db → 页面刷新数据立刻变化，**不需要重启进程**。

### 第 2 步：未登录跳转登录页 —— `src/error.rs`

`AppError::Unauthorized` 的响应从 `(401, "请先登录")` 改成
`Redirect::to("/login")`（302）。
加注释说明：M8 的 API 会用自己的 ApiError 返回 401 JSON，这里只管页面。

### 第 3 步：排序真值 —— `src/handlers/plan.rs`

1. **模板创建**（template_create）：
   ```rust
   let next_sort = sqlx::query_scalar::<_, i64>(
       "SELECT COALESCE(MAX(sort_order), -1) + 1 FROM templates WHERE phase_id = ?",
   )
   .bind(&phase_id)
   .fetch_one(&pool)
   .await?;
   ```
2. **模板列表**（list_templates）：加 `ORDER BY sort_order, id`。
3. **编辑页顺序兜底**（template_update / plan_update）：
   - 每行加 `<input type="hidden" name="order_{ex_id}" value="{当前展示序号}">`
   - JS `addRow`：新行的 order = 当前表格里最大 order + 1
   - 后端：从 flatten HashMap 里过滤 `order_` 前缀键 → 按 order 排序
     → 再 `enumerate()` 分配 sort_order（先删后插时用）
4. 验证：编辑计划把动作顺序打乱 → 保存 → 刷新，顺序与编辑时一致。

### 第 4 步：统一样式 + 响应式 + PWA 全页面铺开 —— `src/page.rs` + `static/style.css`

1. 新建 `static/style.css`：基础排版（字体/间距）、表格样式、按钮样式、
   手机媒体查询（窄屏不横向滚动）。不要求清掉所有内联样式，先整体不难看。
2. 新建 `src/page.rs`，写公共头函数（M6 只给 today/home 铺了 PWA，这次全铺）：
   ```rust
   /// 公共 <head>：charset + viewport + CSS + manifest + SW 注册
   pub fn page_head(title: &str) -> String
   {
       format!(
           r#"<head>
           <meta charset="UTF-8">
           <meta name="viewport" content="width=device-width, initial-scale=1.0">
           <title>{title}</title>
           <link rel="stylesheet" href="/static/style.css">
           <link rel="manifest" href="/static/manifest.json">
           <script>
               if ('serviceWorker' in navigator) {{
                   navigator.serviceWorker.register('/sw.js');
               }}
           </script>
           </head>"#,
           title = title,
       )
   }
   ```
3. 把**所有页面**的手写 `<head>` 替换成 `page_head(...)` 调用
   （home / today / plans / record / history / backup / auth / exercises / phases…）。
4. 顺手补齐空态：计划列表空、历史无记录、today 无计划 → 友好提示
   （有的一直是裸提示，统一配上样式）。

### 第 5 步：PWA 离线数据 + 图标 —— `sw.js` + `static/manifest.json`

1. `sw.js` 的 fetch 改成按请求分流：
   - `/static/` 开头 → **Cache-first**
   - 其余 GET 页面 → **Network-first**（成功就存缓存，失败回缓存）
2. 生成两个图标 `static/icon-192.png` / `static/icon-512.png`
   （纯色底 + 文字即可，ImageMagick：
   `convert -size 512x512 xc:'#2196f3' -gravity center -fill white -pointsize 256 -annotate 0 '练' icon-512.png`）。
3. `manifest.json` 加 `icons` 字段，`theme_color` 与图标底色一致。
4. 验证：访问 today → 断网刷新 → 显示**上次的数据**（不只是静态壳）。

### 第 6 步：部署文档 —— `docs/deploy.md`

写 systemd 部署说明：
- unit 文件模板（/etc/systemd/system/train_record.service）：
  ```ini
  [Unit]
  Description=train_record web server
  After=network.target

  [Service]
  WorkingDirectory=/opt/train_record
  ExecStart=/opt/train_record/train_record
  Environment=PORT=80
  Environment=DATABASE_PATH=/var/lib/train_record/train_record.db
  Environment=BODY_PART_ORDER=腿,背,胸,核心,手臂,肩
  Restart=on-failure
  RestartSec=3

  [Install]
  WantedBy=multi-user.target
  ```
- 升级流程：备份 DB + static → 构建 → 拷二进制 + static → `systemctl restart`
- 日志：`journalctl -u train_record -f`
- 开机自启：`systemctl enable train_record`

**第 1 题**：Arc 管**共享所有权**（多个 handler 同时持有同一份 pool），
RwLock 管**可变性**（读锁并发查询 / 写锁独占换池）。

**第 2 题**：旧连接池持有**旧文件的句柄（连接）**，不关直接覆盖会**损坏数据库**。

**第 3 题**：401 是给**程序/API 客户端**看的（JSON 状态码），
302 是给**人（浏览器）**看的（自动跳转登录页）。

修复：每行加 **`order_{ex_id}` 隐藏序号**字段，后端按它排序后再分配 sort_order。

**第 5 题**：Cache-first 是**命中缓存直接返回**（快，静态资源用），
Network-first 是**先问网络、失败回缓存**（永远最新，页面数据用，断网兜底）。
