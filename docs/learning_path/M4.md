## 一、M4 要做什么（一句话）

**让"训练时"能把实际完成情况记下来**：今日页展示当天计划 → 每个动作可录入实际重量/组数/次数/感受 → 保存落库（records 表）。

M3 做到了"训练前把今天要练什么排好"（计划），M4 补上"训练中把实际练了什么记下来"（记录）。
记录是 M5 历史回顾/渐进超负荷分析的数据来源——**M4 是整个系统的核心闭环**。

## 二、核心概念（先理解再动手）

### 2.1 数据流：计划 → 记录（闭环）

```
计划 Plan（训练前） ──训练──▶ 记录 Record（训练后）
  计划项 plan_items                每条 = 一个动作的一次完成记录
  动作 6: 卧推 4组×8次              Record { weight: 60, sets: 4, reps: 8, ... }
```

- 记录**挂在计划项**上（`plan_item_id`），也**挂在阶段**上（`phase_id`）——双挂靠
- 计划是"预期"，记录是"实际"——**两者独立**（计划可改，已产生的记录不变）
- 一条记录 = 一个动作一次训练的全部组数汇总（不是每组一条！见 2.3）

### 2.2 records 表长什么样（M2 就建好了）

| 列 | 说明 |
|----|------|
| `plan_item_id` | 关联的计划项（从计划录入时填；可空 = 自由录入） |
| `phase_id` | 所属阶段 |
| `exercise_id` | 动作 |
| `record_date` | 记录日期 'YYYY-MM-DD' |
| `weight` | **实际总重** kg |
| `sets` / `reps` | 实际组数 / 次数 |
| `rest` | 组间休息秒 |
| `feeling` | 感受（自由文本） |
| `strategy` | 策略/后续安排（渐进超负荷的关键输入！） |
| `key_points` | 当次要领（预填动作库的要领，可改） |
| `mode` | 录入时模式（bar/support/std/lb2kg） |

### 2.3 记录粒度：一个动作一次训练 = 一条记录（不是每组一条！）

**这是本设计最容易误解的点**：
- 计划项 `plan_items` 一行 = 动作 6 在这个计划里（如"卧推 4×8"）
- 记录 `records` 一行 = 动作 6 在某天的**实际完成**（如"60kg × 4组 × 8次"）
- **不是**每组一条记录（组数只是记录里的一个数字 `sets`）

为什么？—— 渐进超负荷看的是"每次训练这个动作的 重量×组×次"趋势，
一组一条会让历史表爆炸且难以对比。原 sys.py 也是这个粒度。

### 2.4 坚持天数（今日页顶部）

`已坚持 N 天 = 今天 − 阶段.start_date`（用 SQLite `julianday` 计算，避免 Rust 端时区偏差）
```
SELECT CAST(julianday('now','localtime') - julianday(?) AS INTEGER)
```
`start_date` 为 NULL → 显示"未设置开始日期"。

### 2.5 重量换算器（前端内嵌，纯 JS）

训练中常要"片重 → 总重"换算：
- **bar**（杠铃）：总重 = 杆重 + 2×片重（杆重按动作 `bar_weight` 默认带入，可改）
- **support**（自重/支撑器械）：总重 = 体重 − 支撑量
  （支撑器械标的是"帮你抵消多少体重"，如 90kg 体重 + 30kg 支撑做引体 → 实际负重 60kg）
- **std**（器械）：总重 = 片重（机器配重直接读数）
- **lb2kg**（磅制）：总重 = 片重 × 0.4536

M4 用**纯前端 JS**（`static/` 下一个脚本）实时计算，输入片重立刻显示总重，一键填入重量输入框。不做后端换算——换算只是输入辅助，不是业务逻辑。

## 三、M4 要做什么（分步）

### 第 1 步：今日页（GET /today）

文件：`src/handlers/record.rs`（新建）+ `src/main.rs`（注册路由）

| 路由 | 方法 | 功能 |
|------|------|------|
| `/today` | GET | 今日训练页 |

逻辑：
1. 守卫 `AuthUser` + 查当前用户**进行中的阶段**（未归档；若多个取最新，若没有 → 空态提示"暂无进行中阶段，请先创建"）
2. 查今天日期 `SELECT date('now','localtime')`（与计划创建一致）
3. 查今天的计划：`SELECT * FROM plans WHERE phase_id = ? AND date = ?`（可能没有 → 提示"今天还没有计划"）
4. 有计划 → 查计划项（`SELECT * FROM plan_items WHERE plan_id = ? ORDER BY sort_order`）
5. 查动作名——**不 JOIN**，用 M3 同款模式：查全部动作 → 建 `HashMap<i64, String>`（id → 名字）索引。
   为什么不用 JOIN？`query_as` 按列名匹配结构体字段，JOIN 多出的 `exercise_name` 列
   与 `PlanItem` 不匹配（无法 `query_as::<_, PlanItem>`）。M3 的 plan.rs 也是这个做法：
   "查两次 + 内存索引"，避免定义新结构体。
6. 查每条计划项的**最近一条记录**（判断"已训练"状态徽标 + 上次策略提示）：
   ```
   SELECT * FROM records WHERE plan_item_id = ? ORDER BY record_date DESC, id DESC LIMIT 1
   ```
   （N+1 查询在数据量小可接受；M5 再优化成一次 JOIN）
7. 顶部：阶段名 + 坚持天数 + 日期；列表：每动作 → 动作名、计划值、状态徽标（✅已训练/⬜未训练）、上次策略提示

### 第 2 步：单动作记录/编辑页（GET /plans/{id}/record/{item_id}）

| 路由 | 方法 | 功能 |
|------|------|------|
| `/plans/{id}/record/{item_id}` | GET | 单动作记录表单 |

逻辑：
1. 验证：计划属于当前用户（JOIN phases）+ 计划项属于该计划（`WHERE id = ? AND plan_id = ?`）
2. 上半区：计划值（sets/reps/weight，可改？——M4 先只读展示计划值）+ **上次记录参考**（该动作上一次记录的实际值/感受/策略，若存在）
3. 下半区：录入表单——实际重量（**含换算器**）、组数、次数、休息、感受、策略、要领（预填动作库 `key_points`）
4. 若该计划项**已有记录** → 表单预填旧值（编辑模式），页面上显示"更新记录"

### 第 3 步：保存记录（POST /plans/{id}/record/{item_id}/save）

| 路由 | 方法 | 功能 |
|------|------|------|
| `/plans/{id}/record/{item_id}/save` | POST | 保存（插入或更新）记录 |

逻辑：
1. 验证归属（同上）
2. 表单结构体：`weight: f64, sets: i64, reps: i64, rest: i64, feeling: String, strategy: String, key_points: String, mode: String`
3. **已有记录 → UPDATE**（按 plan_item_id 找最新一条更新）；**没有 → INSERT**（`plan_item_id` 记上）
4. 插入时 `phase_id` / `exercise_id` 从计划项 JOIN 取，`record_date` = 今天
5. 保存成功 → 重定向回 `/today`（今日页会显示 ✅ 已训练）
6. 校验：weight/sets/reps 必须 ≥ 0（负数 → 422 Validation）

### 第 4 步：重量换算器（前端 static/）

文件：`static/weight_converter.js`（新建）+ 记录页引入 `<script src="/static/weight_converter.js"></script>`

逻辑（纯 JS，不碰后端）：
1. 页面上：模式下拉（bar/support/std/lb2kg）+ 片重/支撑量输入 + 杆重输入（仅 bar 模式显示）+ 体重输入（仅 support 模式显示）+ 换算结果 + "填入重量"按钮
2. `oninput` 事件实时计算并显示总重（support = 体重 − 支撑量，体重用 localStorage 记住）
3. 杆重初始值 = 页面里从动作 `bar_weight` 渲染出的数据属性（`data-bar-weight`）
4. 点"填入重量" → 把总重写进实际重量输入框

### 第 5 步：home 加入口

`src/main.rs` 的 home 里"训练管理"区加一行：`<li><a href="/today">今日训练（记录）</a></li>`

### 第 6 步：M4 验收 + 理解验证

见下文第五、六、七节。

## 六、M4 常见坑

| 坑 | 解决办法 |
|---|---|
| 记录粒度搞错（每组一条） | 一条记录 = 一次训练的动作汇总，`sets` 是数字不是多条记录 |
| 日期用 Rust 端 `chrono` | 统一用 SQLite `date('now','localtime')`，和计划/记录落库一致 |
| 计划项不属于该计划 | 查询必须 `WHERE id = ? AND plan_id = ?`（双条件，防越权传别人的 item_id） |
| 已训练动作重复 INSERT | 先查 `plan_item_id` 有没有记录：有 → UPDATE，无 → INSERT（Upsert 语义） |
| 换算器 JS 拿不到杆重 | 用 `data-bar-weight` 属性从后端渲染的 HTML 传给 JS |
| 负数重量/组数 | 校验 `>= 0`，否则 422 |
| 坚持天数算错 | 用 `julianday` 相减取整，NULL start_date 单独处理 |
| 大括号换行 | 项目约定：函数体左大括号换行（Allman 风格） |
| 禁止 unsafe（项目规则） | 任何地方都别用 unsafe |

**第 1 题**：一条记录 = 一个动作在某天训练的**实际完成汇总**（全部组数汇总），
不是每组一条。`sets` 字段存的是**组数**（一个数字）。

**第 2 题**：因为同一天同一计划项只应有一条记录——再次保存是**更新（改旧值）**，
不是新增。判断依据是 **`plan_item_id`**（这个计划项有没有记录：查得到 → UPDATE，查不到 → INSERT）。

**第 3 题**：计划是训练前的**预期安排**，记录是训练后的**实际完成**。
修改计划**不会**影响已产生的记录——因为记录独立存于 records 表（记录有自己的一份数据）。

> ⚠️ **M4 后补充（实际使用中发现的坑）**：修改计划虽然**不删记录数据**，
> 但 `plan_update` 的先删后插会重建 plan_items（新 id），若不同步把
> `records.plan_item_id` 挂回去，记录就**失去关联**（显示"未训练"）。
> 修复详见 `M4_bugfix_notes.md` §11——"备份-重建-还原"三阶段。

**第 4 题**：坚持天数 = 今天 − **阶段 start_date**，用 SQLite 的 **`julianday`** 函数计算日期差。
`start_date` 为空时要**显示"未设置开始日期"**（不能报错）。

**第 5 题**：从 **records 表**查该动作的**最近一条记录**（同一 plan_item_id），
按 **record_date（日期）** 排序取最新一条。
策略提示的价值是：训练前看上次的**策略**，决定这次是否加重量（渐进超负荷）。
