## 二、四问四答（M5 前定位）

### Q1：这算小型还是中型项目？

**小型（偏上限）。** 行数、单体架构、单库、单用户都是小型特征；
但"完整度"（真实生产闭环）让它区别于练手玩具。

### Q2：做完算不算入门 web 后端？离传统后端程序员多远？

**入门了，且是货真价实的入门。** 已覆盖：HTTP 语义、会话认证、
关系数据库（外键/事务/迁移）、数据隔离、生产部署运维。

**与"传统 web 后端程序员"的真实差距**（按重要性排序）：

| 差距 | 说明 |
|---|---|
| API 设计 | 现在是服务端渲染表单；现代后端主战场是 REST API / JSON 接口 |
| 并发与性能 | 单用户 SQLite，未碰连接池调优、N+1、缓存、索引设计 |
| 测试体系 | 只有 2 个单元测试；真实后端要求 handler 级集成测试 |
| CI/CD | 手动部署；企业是流水线自动构建部署 |
| 生态广度 | 未用过 Postgres/MySQL、Docker、Redis、消息队列、gRPC |

**一句话**：已经是"能独立做出可用后端系统"的人；
中间隔着的大多是**协作与规模**课题，不是编程本身。

### Q3：不为工作，只想加 web 开发技能树——够不够？

**够了，且绰绰有余。** 技能树的含义是"未来任何需要时能自己搭一个能跑的系统"——
这个能力已达成（全链路走过一遍 + 真实生产 bug 判断力）。
剩余缺口（Docker/CI/API）对非职业场景几乎用不上，继续深造是兴趣驱动，非必要。

### Q4：无辅助重写一遍，还是开下一个工程？

**开下一个工程。** 理由：

1. 重写的最大收益（肌肉记忆）在日常迭代中已持续获得
2. "无辅助重写"难以执行——会不自觉回忆出原实现（变成默写，不是独立）
3. **关键原则：新工程必须逼自己写"没写过的东西"**；
   若 80% 代码能在 train_record 找到对应，就是变相重写

## 三、GUI 技术栈决策（同轮讨论，记录在案）

### 需求约束

- 学习时间充足，**不考虑学习曲线**（有 AI 辅助）
- **不要 Electron**（拒绝套壳 Chromium）
- 既定目标框架：iced（`M4_bugfix_notes.md` 每个知识点表都标注"iced 会重演吗"）

### 决策：另开 workspace crate 做 iced 桌面客户端 + REST API

| 方案 | 结论 | 理由 |
|---|---|---|
| A. 与现有工程放一起 | ❌ | 数据在云端，GUI 无法直连远程 SQLite，放一起只剩编译耦合坏处 |
| B. 另开仓库/workspace 做客户端 | ✅ | 经典客户端-服务器分离；逼出 REST API（最大技能缺口）；编译隔离保 target 纪律 |
| C. wasm | ❌ | 前端极轻无性能收益；wasm 仍是浏览器体验，不满足"桌面应用"目标 |

**性能对比**（iced/egui/Slint 均为原生，冷启动 <1s、内存 10-80MB，
甩 Electron 一个量级）→ **选定 iced**（保留模式与"状态投影"思想一脉相承）。

### 路线图

```
M5 收官（历史回顾）
  → M6 给 train_record 加 REST API 层（/api/v1/... JSON）★ 传统后端必修课
  → M7 另开 workspace crate：iced GUI 客户端
     （登录 → 今日计划 → 记录 → 图表；calc.rs 等纯逻辑跨 crate 共享）
```

### 两条红线

1. **移动端继续用 web 版**：健身房场景用手机浏览器，iced 替代不了；
   GUI 定位是"电脑上做计划编辑/数据分析/看大图表"的管理工具
2. **不做离线同步**：客户端在线使用，数据即时走 API 落库；
   离线同步引入 CRDT/冲突合并，复杂度爆炸，学习项目不碰
