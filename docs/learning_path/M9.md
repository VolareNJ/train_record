## 一、M9 要做什么（一句话）

**给 train_record 再加一层 gRPC 服务（`/train_record.v1.*`，默认端口 50051）**——
把已经跑通的 REST 业务逻辑，用"强类型契约 + 原生流式"的方式再输出一遍，
让桌面客户端（M10）拿到更适合程序消费的接口。

M8 之后项目有三种出口：

```
手机浏览器 ──▶ handlers/   SSR      拼好的 HTML      （人看，日常记训练）
curl/脚本  ──▶ api/rest/   REST     JSON over HTTP   （调试、外部工具）
iced 客户端 ─▶ api/grpc/   gRPC     Protobuf over HTTP/2（M9 新增，强类型 + 流式）
                  │
                  ▼
            同一个 SQLite + 同一套业务函数
```

### 为什么值得学 gRPC？它到底比 REST 强在哪

| 能力 | REST | gRPC | 本项目怎么用 |
|------|------|------|--------------|
| 契约检查 | 文档 + 手写解析，写错运行时才发现 | **IDL 生成代码，写错编译不过** | `proto/train_record.proto` |
| 流式 | 只能"一次性大数组"（SSE/分块要自己造） | **4 种 RPC 类型原生支持** | 1RM 序列、导出、批量提交、实时回执 |
| 传输 | JSON（人可读，体积大） | Protobuf（二进制，体积小） | 同一条记录，gRPC 传的字节更少 |
| 多语言 | 各自写 HTTP 客户端 | 同一份 proto 生成任意语言 | 将来写 Python 分析脚本零成本 |
| 浏览器友好 |  天然 |  需要 grpc-web 代理 | 所以**网页版继续走 REST**，不是替换 |

**一句话结论**：REST 与 gRPC 不是替代关系，而是两种"出口"。
本项目保留 REST（浏览器/脚本/调试方便），新增 gRPC（客户端强类型 + 流式）。

## 二、核心概念（先理解再动手）

### 2.1 IDL 与代码生成：契约第一次成为"代码"

M8 的 REST 契约写在 `docs/api.md` 里，是**给人看的**：
字段拼错、类型写错，编译器一无所知，只有客户端跑起来才报 422/500。

M9 的契约写在 `proto/train_record.proto` 里，是**给编译器看的**：

```
proto/train_record.proto
        │  protoc（构建时自动跑，见 build.rs）
                  ▼
target/.../out/train_record.v1.rs   （生成的 Rust 代码，不提交进 git）
        │  tonic::include_proto!("train_record.v1")
                  ▼
src/api/grpc/mod.rs 里的 pub mod pb { ... }
                  │
        ├─▶ 服务器侧：pb::phase_service_server::PhaseService（要实现的 trait）
        └─▶ 客户端侧：pb::phase_service_client::PhaseServiceClient（直接可用）
```

三个"想不到但现在能享受到"的好处：
1. **服务器和客户端共用同一个类型**——改字段名，客户端编译立刻失败（而不是线上 500）
2. **生成代码不提交进仓库**（build.rs 生成），proto 是唯一事实来源
3. **对端代码白送**：写服务器时客户端已经生成好了（M9 的冒烟测试就是这么来的）

### 2.2 四种 RPC 类型：gRPC 真正的差异化能力

| 类型 | proto 写法 | 本项目实例 | 适用场景 |
|------|-----------|-----------|---------|
| 一元（unary） | `rpc A(Req) returns (Resp)` | 30 个方法中的 29 个 | 常规一问一答 |
| 服务器流 | `rpc A(Req) returns (stream Resp)` | `StreamExerciseSeries`、`StreamRecords` | 画图、导出 |
| 客户端流 | `rpc A(stream Req) returns (Resp)` | `SubmitWorkout` | 批量提交后要汇总 |
| 双向流 | `rpc A(stream Req) returns (stream Resp)` | `LiveSession` | 边发边收（实时回执） |

Rust 侧的写法差异（这是 M9 最主要的新知识）：

```rust
// 一元：request 里就是消息本身
async fn get_phase(&self, request: Request<GetPhaseRequest>) -> Result<Response<Phase>, Status>

// 服务器流：要给关联类型指定"流的具体类型"（不能用 dyn，项目纪律）
type StreamExerciseSeriesStream = tokio_stream::Iter<IntoIter<Result<Point, Status>>>;
async fn stream_exercise_series(&self, request: Request<SeriesRequest>)
    -> Result<Response<Self::StreamExerciseSeriesStream>, Status>

// 客户端流：request 里是"读取器"，要循环 message() 读到 None
async fn submit_workout(&self, request: Request<Streaming<UpsertRecordRequest>>)
    -> Result<Response<SubmitWorkoutSummary>, Status>

// 双向流：入是读取器，出是流的类型（本项目用 mpsc + ReceiverStream）
type LiveSessionStream = ReceiverStream<Result<LiveSetFeedback, Status>>;
async fn live_session(&self, request: Request<Streaming<UpsertRecordRequest>>)
    -> Result<Response<Self::LiveSessionStream>, Status>
```

**注意流元素的类型永远是 `Result<T, Status>`**：协议层面允许"流到一半出错"，
所以每条消息都自带状态位（不是"要么全成功要么全失败"）。

### 2.3 错误模型：Status 不是 HTTP 状态码

REST 的错误 = 状态码 + JSON body；gRPC 的错误 = **状态码枚举 + message（放 trailer）**。

| REST/HTTP | gRPC Code | 数字 | 本项目来源 |
|-----------|-----------|------|-----------|
| 401 Unauthorized | `UNAUTHENTICATED` | 16 | `ApiError::Unauthorized`、缺 token |
| 403 Forbidden | `PERMISSION_DENIED` | 7 | `ApiError::Forbidden`（归档阶段不可编辑） |
| 404 Not Found | `NOT_FOUND` | 5 | `ApiError::NotFound`（含跨用户越权） |
| 400 Bad Request | `INVALID_ARGUMENT` | 3 | `ApiError::Validation` |
| 500 | `INTERNAL` | 13 | `ApiError::Database` / `Other` |

**为什么不能直接返回 302/HTML？** 与 M8 §2.3 同一个道理：
客户端是程序，它要的是"明确的失败信号"，不是给人看的跳转或页面。

**Rust 侧的爽点**：`From<ApiError> for Status` 实现一次之后，
service 里就能一路 `?`（注意：本项目 M9 起统一**全路径**写法，见 §2.7）：

```rust
let out = crate::api::rest::phases::phase_list(&pool, user.id).await?;  // ApiError 自动变 Status
```

（`?` 会自动调用 `From::from`——这是 Rust 错误处理的核心机制，M9 请务必体会。）

### 2.4 认证：Cookie 换成 metadata

| | REST（M8） | gRPC（M9） |
|---|---|---|
| 登录产物 | `Set-Cookie: session=xxx` + body 里的 token | 响应消息里的 `token` 字段 |
| 后续携带 | 浏览器自动带 Cookie | 客户端手动带 metadata |
| 服务端读取 | `extract_token(&headers)` | `auth::require_user(&request, &state)`（全路径：`crate::api::grpc::auth::require_user`） |

客户端（iced / grpcurl）每次调用的写法：

```
metadata: authorization: Bearer <token>
（也兼容 x-session-token: <token>，方便手打）
```

**为什么不做成"拦截器统一守卫"？** 见 `src/api/grpc/auth.rs` 顶部注释：
tonic 的 `Interceptor` 拿不到 AppState、也难表达"哪些方法免登录"，
个人项目里"每个方法第一行显式守卫"更好读。这是一个**有意识的选择**，
不是"不支持中间件"。

### 2.5 复用策略：M8 那句"先复制，后抽取"在这里兑现

M8 §2.5 写过：

> M8 的做法：**先复制，后抽取**。第一版 API handler 可以直接写 SQL（快速跑通），
> 当发现同一查询在 2 个以上 handler 出现时，抽成公共函数。

M9 就是那个"第二处"。所以本阶段的**前置重构**（老师已完成，你只需阅读）：

1. **目录归并**：`src/api/*.rs` → `src/api/rest/*.rs`
   （gRPC 加进来后再混在一起，就分不清"哪种协议的错误"了）
2. **REST 层抽出 27 个 `pub(crate)` 函数**（协议无关：只吃 `pool` + `user_id` + 业务参数）

```
抽取前（M8）                        抽取后（M9）
─────────────────────────          ─────────────────────────────
handler {                          handler {           ← 只管 HTTP
    let pool = ...;                     let pool = ...;
    sqlx::query(...)   ← SQL           Ok(Json(phase_list(&pool, user.id).await?))
    ... 20 行                          }
}                                  phase_list(pool, user_id) {  ← 协议无关
                                       sqlx::query(...)  ← 同一份 SQL
                                   }
                                        ▲
                                        │  gRPC 也调它
                                   grpc service 层
```

**读代码时的定位口诀**：
- 签名里出现 `State` / `ApiAuthUser` / `Path` / `Json` → 这是 HTTP 适配层（薄）
- 签名里只有 `&SqlitePool` / `user_id` / 业务参数 → 这是共享业务层（厚，SQL 在这）

> 抽取后的函数名一览（实现 gRPC 时你会用到）：
> `phase_list/phase_detail/phase_create/phase_update/phase_set_archived`、
> `exercise_list/exercise_detail/exercise_create/exercise_update/exercise_delete`、
> `template_*_impl` / `plan_*_impl`（plans.rs 的 handler 占了原名，故加 `_impl` 后缀）、
> `today_view/record_upsert/record_update/record_delete/records_range`、
> `calendar_view/day_records/exercise_stats_view`。
> 完整清单见各文件里带 `协议无关实现（REST handler 与 M9 gRPC 服务共用）` 注释的函数。

### 2.6 proto3 的三个"坑"（契约设计纪律）

1. **普通标量没有"未设置"**：`string note = 2;` 无法区分"没传"和"传空串"。
   要 PATCH 语义必须写 `optional string note = 2;`（生成 `Option<String>`）。
   → 本项目的所有 `UpdateXxxRequest` 都带 optional。
2. **字段编号 = 线上的身份**：`= 3` 不是默认值，是二进制里的位置。
   发布后不能改编号；删字段要把编号写进 `reserved`。
3. **契约里不能有"静默谎言"**：客户端能传的字段，服务器必须真的用得上。
   例：`TemplateItemInput` 只有 `exercise_id`——因为 REST 写入路径目前只落这一个字段
   （模板项的组数/次数由动作库默认值决定）。想支持预设 → 加字段 + 加实现，
   而不是"留个字段假装支持"。

### 2.7 写作约定：全路径优先（M9 起生效，详见 AGENTS.md）

M9 开工时做了一次全仓重构（仅调风格，不改行为——重构后冒烟测试仍全绿）：
**除 trait 方法调用必需的导入外，不再有任何 `use`**。所以你写 M9 代码时：

```rust
//  全路径：看着长，但不必回文件头查“这个名字哪来的”
let out = crate::api::rest::phases::phase_list(&pool, user.id).await?;
sqlx::query_as::<_, crate::models::User>("SELECT * FROM users WHERE username = ?")

//  唯一例外：trait 方法调用（trait 必须在作用域里）——按“最小引用”只导那一个
use axum::response::IntoResponse;   // 为了 .into_response()
use argon2::PasswordHasher;         // 为了 .hash_password()

//  不要：把类型/函数 use 进来写短名（M8 时代写法）
use crate::api::rest::phases::PhaseOut;
```

判断口诀：**“能用路径表达的，就不用导入表达”**。
两个历史包袱也在本次重构里清掉了（当作“为什么”的例子看）：
1. `pub use rest::ApiError;` 兼容转发 → 删掉，统一写 `crate::api::rest::ApiError`
2. 能换成 str 自带的 `.parse::<T>()` 就不 `use std::str::FromStr`（少一个 trait 导入）

自查命令（M9 验收要求）：`grep -rn "^use " src/` —— 应只剩下 5 行，且全是 trait。

**同期的另一条约定：全文禁止 emoji**（代码/注释/文档/提交信息），
状态写文字（“已完成 / 待实现”）、清单用 `- [x]`、重点写“注意：”。
原因：终端与编辑器对 emoji 宽度/变体选择符处理不一致，容易错位，
且 grep/日志里搜不到——纯文本更可检索。

**还有一条结构调整：lib + bin 分离**（模块树移到了 `src/lib.rs`）。
你写 M9 代码时：库内文件照旧写 `crate::...`；只有 `src/main.rs`（bin）
引用库要写成包名开头（`train_record::api::rest::router()`）。

### 第 1 题

不行。proto3 的普通标量**没有"未设置"状态**：`string name = 2;` 里"没传"和"传空串"
在 wire 上长得一样（都是默认值 `""`），服务器无法区分"用户想把名字改成空"和
"用户根本没说名字"。而 PATCH 语义的核心恰恰是"没传 = 不改"（REST 侧靠 serde 的
`Option` 做到）。加 `optional`（proto3 显式存在性）后生成 `Option<String>`：
`None` = 没传（不改），`Some("")` = 明确要改成空串，语义就完整了。

### 第 2 题

用 `Status::unauthenticated`（Code 16，对应 HTTP 401）。
不能返回 302 是因为**消费者是程序**：302 是"给人看的跳转指令"，gRPC 里的等价物
是"跟着去拿另一个东西"——客户端要么跟丢，要么拿到不是它期望的结构（页面 HTML），
然后解析失败。程序需要的是**明确的失败信号**（code + message），据此决定
"弹登录框"还是"重新登录"。这是 M8 §2.3 同一个道理的第二次出现——
协议适配层的错误表达必须服务于"谁在读"。

### 第 3 题

因为 Rust 里"异步序列"是 `Stream`（async 版的 Iterator），而 tonic 生成的 trait
里只声明了"有一个关联类型必须实现 Stream"（**关联类型不能是 `dyn Stream`**——
trait 对象带生命周期/对象安全问题，且项目纪律要求避免 dyn）。
所以实现方必须给出一个**具体类型**：本项目用 `tokio_stream::Iter<IntoIter<...>>`
（先算完再逐条发）或 `ReceiverStream<...>`（边算边发）。
流元素必须是 `Result<T, Status>`，因为流是**多次**响应：协议要允许"前几条成功、
第 N 条出错"，客户端在每条消息上都能看到状态位；返回裸 `T` 就无法表达中途失败。

### 第 4 题

- `Result`：这次"读一条"这个动作本身是否成功（`Err(Status)` = 连接坏了/超时/服务器发错）
- `Option`：流是否已经**正常结束**（`None` = 客户端已经 half-close，发完了）
- `T`：真正的一条消息（`UpsertRecordRequest`）

所以惯用写法 `while let Some(item) = stream.message().await?` 正好把两层拆开：
`?` 把 `Err` 抛给调用方，`while let Some` 在 `None` 时干净退出循环。
记忆点：**`?` 处理"错没错"，`Some/None` 处理"还有没有"。**

### 第 5 题

任答两条即可：
1. **单一事实来源（避免 SQL 漂移）**：同一查询写两遍，改一处忘另一处 →
   两个出口返回的数据不一致，而这种 bug 极难发现（页面对了、客户端错了）。
2. **业务规则只写一遍**：数据隔离（`WHERE user_id = ?`）、upsert 语义、
   事务/commit 纪律（AGENTS.md 的重点）、校验顺序——这些一旦复制就有走样的风险。
3. **协议层保持薄**：gRPC 层只做"翻译"（metadata→User、DTO→proto），
   换协议（以后再加 CLI/WebSocket）不用重写业务。
4. **测试成本**：M8 那些函数已经被 REST 用过一遍（生产验证过），
   gRPC 复用等于继承了一份"已测试"的实现。

### 第 6 题

因为 `LiveSession` 的回执是**对请求的应答**，而请求是**随时间陆续到达**的：
客户端发第 1 组时，服务器还不知道第 2 组是什么，所以不可能"先算完所有回执再返回"。
必须"边收边发"，这就需要一个**生产端与消费端并发**的通道：
`mpsc::channel` 提供管道，`tokio::spawn` 里的任务负责收消息/落库/发回执，
而方法立刻把管道的接收端包成 `ReceiverStream` 返回给 tonic（tonic 从里面取消息发回客户端）。
`tx.send(...)` 返回 `Err` 表示**接收端没了**（客户端断开或取消调用）——
此时必须 `break` 结束任务；否则服务器会留下一个永远在等待的任务（任务泄漏：
占着内存和连接，永远不会有人来收它的回执）。
（另外：channel 的容量（本项目 16）同时也是**背压**机制——客户端读得慢，
send 就会等待，服务器自然慢下来。）
